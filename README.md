# kz-labor-rag

RAG-система вопрос-ответ по Трудовому кодексу Республики Казахстан.

Главный артефакт проекта — **измеренное улучшение качества поиска относительно
намеренно наивного baseline**, а не сам бот. Поэтому eval-харнесс собран раньше,
чем появился RAG, и каждая итерация меняет ровно одну вещь.

Журнал измерений: [EVALUATION.md](EVALUATION.md).

357 тестов, `pytest -q`. Часть тестов идёт против настоящего pgvector или
против скачанного корпуса и пропускается, если базы нет или корпус не скачан.

## Порядок работы

1. Eval-харнесс — до RAG. Метрики проверены на выдаче с заранее известным
   ответом, чтобы им можно было верить, когда появится система.
2. Датасет — до baseline. Разметка после взгляда на выдачу подгоняет метрику
   под систему вместо того, чтобы её измерять.
3. Baseline — намеренно наивный: чанки по 512 токенов без учёта структуры,
   косинусное сходство, без reranking.
4. Итерации — по одному изменению за раз, каждая с прогоном eval и отдельным
   коммитом.

Гейт: пока в датасете нет 60 русских вопросов, 15 казахских, 15 реальных и
ревью человеком, прогон падает с объяснением, а в EVALUATION.md не пишется ни
одной цифры.

## Пополнение датасета

У датасета два источника, и правятся они по-разному.

**Синтетические русские вопросы** задаются таблицей `SPECS` в
`scripts/build_synthetic_dataset.py`. Цитата там не пишется руками: указывается
якорь, а `make dataset` находит его в тексте статьи и вырезает дословный
фрагмент. Якоря, которого в кодексе нет, достаточно, чтобы сборка упала.

**Реальные вопросы и казахский срез** пишутся руками прямо в
`evals/datasets/kz_labor_v1.jsonl`: у реального вопроса формулировка взята из
конкретного треда, и сгенерировать её нельзя. `make dataset` такие строки не
трогает — пересобирается только синтетическая русская часть, всё остальное
переносится как есть. Пустой слот `real_*` создаётся лишь под id, которого в
файле нет.

Цитату при этом всё равно не набирают руками — её вырезает та же функция, что
и при сборке синтетики:

```bash
kzrag-corpus quote 62 "в течение пяти рабочих дней"
```

Команда печатает фрагмент и готовую запись для `evidence`. Перенабранная
цитата расходится с текстом статьи на один символ, и обоснование, которое
человек читает при ревью, перестаёт быть обоснованием.

Проверяются обе части одинаково: схемой и сверкой с корпусом. Цитата, которой
нет в тексте своей статьи, роняет сборку независимо от того, вырезал её скрипт
или вписал человек, — рукописного обоснования «на честном слове» в датасете
не бывает.

```bash
make dataset        # пересобрать синтетику, перенести остальное
make dataset-check  # сверить разметку с текстом кодекса
```

Одна асимметрия: отметку ревью у сгенерированного вопроса защищает отпечаток —
поменялась формулировка или цитата, и отметка слетает сама. У рукописного
вопроса сравнивать не с чем, файл и есть источник, поэтому после правки
отметку надо снимать самому: `kzrag-review unmark <id>`.

## Ревью разметки

Ревью идёт по дословным цитатам из кодекса: в
[evals/datasets/REVIEW.md](evals/datasets/REVIEW.md) у каждого вопроса указаны
обязательные статьи, точный пункт и фрагмент нормы, из которого взят эталон.
Проверять нужно одно: следует ли ответ из процитированной нормы и не пропущена
ли статья, без которой ответ неполон.

```bash
kzrag-review status
```

```bash
kzrag-review mark syn_001 syn_002 syn_003
```

Флаг `reviewed_by_human` — это гейт, а не пометка для памяти: пока хоть у
одного вопроса он `false`, `kzrag-eval run` останавливается.

## Быстрый старт

```bash
cp .env.example .env
```

```bash
docker compose up
```

Это всё. Первый запуск дольше остальных: контейнер сам скачивает текст кодекса,
сверяет контрольную сумму, тянет веса модели эмбеддингов и строит индекс на CPU.
Прогресс виден в логах `api`. Скачанный корпус, веса и кэш эмбеддингов лежат в
томах и переживают пересоздание контейнеров, поэтому повторный `up` — секунды.

После старта: <http://localhost:8000/health> покажет, построен ли индекс и на
какой редакции корпуса.

```bash
curl 'http://localhost:8000/search?q=можно+ли+уволить+в+отпуске'
```

Ключ Anthropic нужен только для `/ask` и для faithfulness. Без него поиск,
recall@5 и MRR работают полностью.

## Индекс

**143 чанка**, стратегия `fixed_tokens`, окно 512 токенов по счёту токенизатора
модели: 507 содержимого плюс префикс `passage: ` плюс служебные токены. В логах
и коммитах до 2026-08-11 встречается 142 — это состояние до фикса переполнения
окна, когда 512 ошибочно считались длиной одного содержимого. Разница не в том,
что один чанк разделился: окно сузилось, границы разъехались с нулевого чанка,
и в тот же поток из 72 486 токенов стало помещаться на одно окно больше
(`ceil(72486/512) = 142` против `ceil(72486/507) = 143`).

## Отладка выдачи

Главный инструмент для пункта «смотрим, где baseline проваливается»:

```bash
kzrag-search "меня уволили пока я был на больничном"
```

```bash
kzrag-search --question syn_001
```

Для вопроса из датасета показывает не только выдачу, но и разбор: на каком
ранге оказалась каждая обязательная статья, покрыт ли точный пункт и что
вытеснило эталон из топ-k.

```bash
kzrag-search --failures
```

Прогоняет весь датасет и печатает только вопросы, где ни одна обязательная
статья не попала в топ-k. Это и есть вход для списка гипотез.

```bash
kzrag-search --article 54
```

Показывает, как статья разрезана на чанки и с какими соседними статьями она
делит чанк, — при наивной нарезке по 512 токенов это главный источник шума.

## Локально, без Docker

Разобрать корпус и посмотреть статистику:

```bash
kzrag-corpus stats
```

Сверить разметку эталона с текстом кодекса:

```bash
kzrag-corpus check-dataset
```

Проверить датасет и гейт готовности:

```bash
kzrag-eval validate
```

Построить индекс (нужна поднятая база: `docker compose up -d db`):

```bash
kzrag-index build
```

```bash
kzrag-index status
```

```bash
kzrag-eval run
```

## Осознанные решения

**Генератор и судья — разные модели.** Sonnet 5 генерирует, Haiku 4.5 судит.
Модель, оценивающая собственный вывод, систематически к нему снисходительна, и
faithfulness получается завышенной. Позже запланирована сверка оценок
судьи-Haiku и судьи-GPT на одном прогоне.

**Промпты неизменяемы внутри версии.** Связка версия→содержимое зафиксирована
хешами в `eval/prompts/REGISTRY.json`. Правка промпта без бампа версии роняет
прогон: метрики, посчитанные разными промптами, несравнимы, а нарушить это
соглашение случайно слишком легко.

**Baseline не получает бесплатных улучшений.** Заголовок статьи не приклеивается
к чанку, ANN-индекса нет, reranking нет. Всё это — отдельные измеряемые
итерации, а не подарок baseline'у.

**В коде нет значений по умолчанию для конфига.** Отсутствие ключа — ошибка, а
не повод молча подставить «разумное» значение: тихий дефолт означает, что строка
в EVALUATION.md не восстанавливается из записанного конфига.

**Чанк засчитывается за все статьи, текст которых в него попал.** Наивная
нарезка по 512 токенов режет по живому: один чанк накрывает в среднем около
четырёх статей. Если засчитывать только ту, с которой чанк начинается, recall
падал бы из-за способа нарезки, а не из-за качества поиска, и разница между
baseline и structure-aware чанкингом оказалась бы артефактом разметки. Слабость
наивной нарезки и так видна — в clause-метриках и в количестве посторонних
статей в выдаче.

**`chunk_size_tokens` — это бюджет кодирования, а не длина содержимого.**
Модель кодирует содержимое плюс префикс `passage: ` плюс служебные токены.
Если считать 512 содержимым, на вход уходит 516–517 при пределе 512, и хвост
отбрасывается молча — без исключения и без строки в логе. Проверено: удаление
«потерянного» хвоста меняет эмбеддинг ровно на ноль. Чанкер вычитает оверхед
сам, причём измерением, а не вычитанием константы: sentencepiece склеивает
префикс с началом текста по-разному, и оверхед гуляет между 4 и 5 токенами.
Индексация падает, если хоть один чанк не влез.

**Индекс знает, чем он построен.** В таблице `index_meta` лежат модель,
подпись чанкинга, отпечаток конфига, хеш файла корпуса и версия парсера. Поиск
поверх векторов от другой модели даёт правдоподобные, но бессмысленные числа,
поэтому несоответствие останавливает прогон, а не проявляется как «почему-то
упал recall».

Сверяется всё, от чего меняются тексты чанков, а не только нарезка и модель.
Идентификатор чанка позиционный, и обычная сборка делает `upsert` без
удаления: новая редакция кодекса, давшая меньше чанков, оставила бы хвост
строк от прошлой, и поиск продолжил бы их возвращать. Поэтому редакция
сверяется по хешу файла — он строже метки в подвале документа, которая при
правке одной статьи может не измениться, — а число строк в таблице сверяется с
тем, что записала последняя сборка.

**Номер статьи — строка, а не число.** В кодексе 223 статьи: 1–204 плюс 19 с
составными номерами (`73-1`, `126-1`, `203-1` …), добавленных поправками. Среди
них нормы про скользящий график, гарантии беременным и вредные условия — то
есть темы, без которых eval-датасет был бы неполным.

**Эмбеддинги: `multilingual-e5-base`.** Модель требует асимметричных префиксов
`query:` и `passage:`; перепутать их — тихая деградация качества без единой
ошибки в логах. Апгрейд до `e5-large` — отдельная запланированная итерация с
замером recall и времени индексации. Ключ кэша эмбеддингов покрывает всё, от чего зависит вектор: версия формата
ключа, модель, `passage_prefix`, флаг `normalize`, подпись чанкинга и текст.
Префикса в ключе сначала не было — и это был баг того же рода, что и
молчаливое усечение: смена префикса вернула бы векторы, посчитанные со старым,
правдоподобные и неверные. Смена модели пишет в соседний файл и не затирает
уже посчитанное.

## Разработка

```bash
make venv
```

```bash
make check
```

Нужен Python 3.12 или новее. `make venv` сам находит подходящий, даже если
`python3` в системе старее, и отказывается собирать venv, когда такого нет:
собранный на 3.11 venv всё равно не переживёт установку проекта, но узнаётся
это уже из вывода pip, где причина выглядит как проблема с зависимостями.
Свой интерпретатор: `make venv PYTHON=/usr/bin/python3.12`.

`make help` покажет остальное: `up`/`down` для стека, `index`/`reindex`,
`dataset` для пересборки синтетической части датасета, `failures` для разбора
провалов поиска.

Тесты pgvector идут против настоящей базы, а часть тестов разметки — против
скачанного корпуса; и те и другие пропускаются, если базы нет или корпус не
скачан (`319 passed, 38 skipped`). Поднять только базу: `make db`.

## Сопоставимость прогонов

Каждый результат eval несёт блок `comparability`: версия метрик, подпись
чанкинга, модель эмбеддингов, sha256 датасета, версии промптов генератора и
судьи. `kzrag-eval compare A.json B.json` отказывается строить таблицу
«до/после», если хоть один ключ разошёлся, и называет виновника.

Подпись чанкинга берётся из `index_meta`, то есть из индекса, на котором поиск
реально работал, а не из конфига. Разница существенная: подпись, считавшаяся по
секции `chunking`, не менялась при смене версии чанкера — и фикс окна модели,
перенарезавший корпус целиком, она бы пропустила.

## Изоляция тестов

Тесты хранилища работают с той же базой, что и боевой индекс, — просто с
другими таблицами. Один раз это уже стоило метаданных: `drop()` сносил таблицу
`index_meta`, имя которой было общим на всю базу. Общие ресурсы и их изоляция:

| Ресурс | Общий | Изоляция |
|---|---|---|
| база `kzrag` | да | таблицы `chunks` против `chunks_test`; метаданные — `{table}_meta` |
| расширение `vector` | да | `CREATE EXTENSION IF NOT EXISTS`, состояние не меняется |
| GIN-индекс по статьям | нет | имя `{table}_articles_idx` привязано к таблице |
| кэш эмбеддингов | нет | тесты создают `EmbeddingCache` в `tmp_path`, `build_encoder` не вызывают |
| датасет, REVIEW.md, реестр промптов | только чтение | правки идут в `tmp_path` |
| `evals/results`, `data/processed` | нет | результаты пишутся в `tmp_path` |

Аудит показал, что сейчас всё изолировано, но ровно это же было верно и до
бага с метаданными. Поэтому набор боевых артефактов снимается до прогона и
сверяется после: сессионная фикстура `production_artifacts_untouched` роняет
прогон и называет конкретный изменённый ресурс. Для каталогов сверяются имена,
размеры и mtime — записи внутрь существующего sqlite-кэша список файлов не
меняет.

## CI

`.github/workflows/ci.yml` гоняет ruff и тесты с сервисом pgvector, а отдельным
job'ом собирает Docker-образ и **проверяет его размер**. Порог в 3 ГБ стоит не
для красоты: без установки torch из CPU-индекса pip притаскивает пакеты
`nvidia` и `triton` и образ раздувается с 1.9 ГБ до 8.7 ГБ. Падение этого шага
означает, что CUDA-зависимости вернулись.
